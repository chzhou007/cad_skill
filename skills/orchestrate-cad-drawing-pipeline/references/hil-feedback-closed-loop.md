# HIL答复导入后的可执行闭环

`pipeline.py hil-feedback` 将答复导入、已确认规则分组、原生重建、独立验证、正式发布和历史回归接入同一执行器。原 `receive-current-review-answers` 仍是归档入口；它的接收回执不能单独代表已应用。使用闭环入口得到最终 `application-ledger.json`。

```text
专家答复与原Pair版本
 → 校验并归档原始答复
 → 受信任规则目录匹配（答复文字只作为数据）
 → 同规则完整实例群体执行 / 已生效且证据有效则保留
 → 原生所有者重建 → 独立原生验证
 → 当前结果发布 → 当前页面实际属性读取及独立发布验证
 → 历史与新增回归门槛 → 应用台账与发布目录
```

## 执行入口

```powershell
python pipeline.py hil-feedback start --config PROJECT.json --output NEW_RUN --cores 16
python pipeline.py hil-feedback status --run NEW_RUN
```

`run` 在当前进程执行；`start` 隐藏启动，日志和阶段收据写入新目录。原始文件、旧结果、旧批注均不覆盖。内部复用 `pipeline_batch_runtime` 的依赖、输入/实现哈希、失败阻断与核数预算；模型无需逐条组织命令或等待每个实例。

## 规则目录与真实状态

配置 schema 为 `cad_hil_feedback_pipeline_v1`，指向固定哈希的 `cad_confirmed_hil_rule_catalog_v1`。目录由维护者填写，不能从专家文本拼装代码。每个规则登记完整问题群、已批准语义、源Pair哈希、输入和原生manifest模板，以及生产、验证、发布、发布验证四个脚本/参数数组。脚本必须是哈希绑定的共享实现。新答复填入manifest明确的receipt槽，不能直接修改最终边属性。

历史记录包含原答复、Pair哈希、原生证明和当前版本证据；证明与当前证据都须有明确JSON断言。记录为 `previous_application_verified`，与本轮重新执行区分。时间戳变化不算新答复；decision/comment或Pair变化不能沿用旧确认。

批处理成功后记录为 `native_applied_regressed_and_published`，必须同时绑定本轮原生证明、验证回执及发布回执。发布器只能修改自己所有的范围；已有范围的同义重放保留后续feature、当前读取链、统一水平/垂直属性与历史批注。实际语义变化须由相应所有者重建依赖并使相关人工确认失效，不能沿用同义重放器。

## 新冲突与技术失败

- 决策矛盾、Pair/源版本变化或新解释进入 `new-conflicts.json/html`，按问题、源版本与语义稳定去重。原答复保留，已确认同类问题不重复询问。
- 有明确归属的冲突只阻断对应规则；独立规则可继续。未知作用范围保守阻断新的应用，不能假定与其他规则无关。
- 缺实现、证据失效、命令失败、完整性或回归失败是 `technical_failure`，保留失败记录，不伪装成新的专家问题，也不能发布成功回执。
- 没有新冲突不等于工程无未知值。未给长度、未完成全图验收及原始输入全链闭合状态继续保留。

## SH16验收口径

批次须验证全部已收答复的历史应用证据，并至少对一个完整真实规则群重新导入、原生执行、独立验证和发布。再检查当前查看器实际有效值、所有历史feature与批注保留。报告分列“存量证据复核”“本轮原生重放”“全量测试”“工程未知与人工验收”，不将一次规则重放宣称为全项目从DWG重新生成。

查看器 `reapply_reviewed_detail_feedback.py` 是当前已审核主详图度量范围的发布适配器；它会独立重算原生所有者并读取正式页面的属性模块。已有范围可同义回灌；需要改动已冻结下游语义时明确拒绝，转交对应依赖重建器，不能静默保留旧值或倒退至旧查看器。
